# 02 还没有 fork 时，0 号任务怎么存在

## 静态对象解决“谁创建第一个任务”

`init/init_task.c` 定义真正的全局 `init_task`。它不是启动后通过 `copy_process` 创建的。编译器和链接器为它生成静态存储；显式初始化给出链表、锁、父指针和资源指针；未显式赋值的静态字段按 C 规则为零，因此 pid/tgid 的初始零值无需写一个 `alloc_pid(0)`。

```c
/* 原码摘录，完整上下文见源码附录 */
.mm             = NULL,
.active_mm      = &init_mm,
.real_parent    = &init_task,
.parent         = &init_task,
.group_leader   = &init_task,
```

`mm=NULL`：没有正常用户地址空间。`active_mm=&init_mm`：此时仍有页表环境。`init_mm` 在 `mm/init-mm.c` 中定义，连接内核初始页表等信息；不能称它为“所有进程共同的用户 mm”。自指针让早期任务在没有外部父任务时也能满足数据结构不变量。

链表初始化成头指向自己表示空链表，不是“有一个子进程就是自己”。区别于 parent 指针自指。`INIT_THREAD`、`INIT_THREAD_INFO`、`init_stack` 及启动汇编提供启动执行环境；`task_struct` 并不自动让 CPU 跳到一个函数。

## x86 启动衔接

检索入口：`arch/x86/kernel/head_64.S` 的 `initial_stack`、`initial_code`，`arch/x86/kernel/head64.c` 的 `x86_64_start_kernel`、`x86_64_start_reservations`，`arch/x86/kernel/cpu/common.c` 的 per-CPU `current_task`。从已有启动课延续到这里即可：CPU 必须已经有有效内核栈、映射和基本 CPU 状态，才进入通用 `start_kernel`。

不要在 BIOS/reset vector 刚停下就打印 `$lx_current()`：此时内核 per-CPU 环境还没有按正常运行状态建立。早期看 `&init_task` 这个静态符号；进入稳定内核阶段后再使用 current 辅助函数。

## start_kernel 的准备不是又造一个 PID 0

本树 `init/main.c:start_kernel` 中主线是：

```text
内存与体系结构早期建立
  → sched_init
  → 中断/时间/其他核心基础设施（有交错，非完整清单）
  → pid_idr_init
  → anon_vma_init
  → fork_init
  → proc_caches_init
  → 其他子系统
  → arch_call_rest_init → rest_init
```

|入口|真正做什么|为什么创建进程前需要它|
|---|---|---|
|sched_init|初始化每 CPU rq、各调度类队列与初始 idle 任务关联|子任务要有队列可入|
|pid_idr_init|为初始 PID namespace 的 PID 分配设施做准备|分配身份前先有管理器|
|anon_vma_init|准备匿名映射的反向映射对象缓存|fork/COW 后追踪匿名页映射|
|fork_init|task_struct 缓存（依配置）、体系结构任务设施、线程数上限等|分配任务描述符和控制数量|
|proc_caches_init|sighand/signal/files/fs/mm/VMA 等相关缓存及后续初始化|不是仅仅初始化 /proc 文件|

本树 `start_kernel` 的一条中文注释把 `proc_caches_init` 简写为“/proc 相关 slab cache”，容易误导。打开 `kernel/fork.c:proc_caches_init` 可以直接看到 `mm_cachep`、`vm_area_cachep` 等分配，不应按函数名望文生义。

`fork_init` 也不是“开始 fork PID 1”。设施初始化是准备分配能力，真正创建在后续 `rest_init`。

## SMP 上不只有一个 idle 执行流

每个在线 CPU 都需要自己的 idle task。启动 CPU 使用静态 `init_task`，其他 CPU 经 `idle_threads_init` / `idle_init` / `fork_idle` 等路径准备自己的 idle task；`init_idle` 绑定具体 CPU。idle 任务使用 PID 0 的特殊身份语义，不是每个都从普通 PID 分配器取一个新的用户 PID。

因此 `swapper/0`、`swapper/1` 末尾是 CPU 编号，不表示 PID 0 和 PID 1。PID 1 是 init。进程树工具通常也不会像列普通进程一样列所有 idle task。

## 跟读任务

1. 打开 `init/init_task.c`，标记 mm、active_mm、stack、flags、父子关系及调度字段。
2. 打开 `kernel/sched/core.c:sched_init`，搜索 `init_idle`，找到如何关联当前启动任务。
3. 打开 `kernel/fork.c:fork_init` 与 `proc_caches_init`，给每个 cache 写“以后哪个 copy_* 用它”。
4. 在 GDB 的 `rest_init` 入口记录 `init_task.pid`、`init_task.mm`、`init_task.active_mm`。这时调度设施已建立，而用户态 init 还没有执行。

验收：能解释“PID 0 的对象已经存在”和“调度器已经能管理任务”是两件事。
