# 15 把课程带到内网，每天能跟着做

## 交付目录不是只含文档

`labs/process_lab.c` 有六个小实验和完整错误检查；`Makefile` 构建；`build-initramfs.sh` 打包最小根文件系统；`run-qemu.sh` 启动；`gdb/boot-verify.gdb` 验证启动；`labs/trace.sh` 用独立 trace instance 捕获调度生命周期。

已提供的 process_lab 是 x86-64 Linux 静态 ELF，不能在 macOS 或 ARM64 构建机上当原生程序直接执行。应放进 x86-64 guest；如果要在 ARM64 Linux 原生运行，需要用对应编译器重新构建，那验证的是 ARM64 主机内核而非本项目 x86-64 内核。

## 六个实验的输入、观察、边界

|命令|操作步骤|应证明|还不能证明|
|---|---|---|---|
|process_lab cow|预写私有页→fork→孩子写→管道确认→父读|子写不改变父值、虚拟地址可相同|没有直接读出初始共享 PFN|
|process_lab exec|fork→记录 PID→exec /proc/self/exe|单线程 exec 保持子 PID|仅日志不能证明新 mm 指针|
|process_lab threads|create→子线程写→join→主线程读|同 PID、异 TID、共享地址与同步结果|不评价竞争性能|
|process_lab fd|fork 后孩子读 AB→wait→父读 CD|同一打开文件描述的偏移共享|不表示 files_struct 指针相同|
|process_lab zombie|_exit(23)→WNOWAIT→读 /proc→waitpid|Z 状态与随后回收|不能断言所有退出都产生 zombie|
|process_lab pipe|孩子 read→父写→wait|阻塞式通信能完成|必须 trace 才确认一次实际睡眠顺序|

`all` 顺序跑六项并输出 PASS。任何关键系统调用失败或验收不满足，会非零退出。实验没有 fork 无限循环、内核模块或故障注入。

## 第一次：自动启动，先证明工具链可用

在 Linux 构建机的仓库根运行：

```bash
CC=x86_64-linux-gnu-gcc bash process-study-2026-09-12/labs/build-initramfs.sh
bash process-study-2026-09-12/labs/run-qemu.sh
```

启动日志应有 Linux 5.15.0、PROCESS_STUDY_BOOT、六项 PASS、PROCESS_STUDY_RESULT=0，然后关机。`PASS exec-child` 是 exec 子映像额外输出，不是第七个独立实验。实际 PID 不必等于本次日志。

使用已有内核与新 initramfs，既能减少首次重建工作，又能单独保存实验环境。若内网已有另一套 rootfs，可把静态 process_lab 拷入 guest 的可执行目录，挂 proc，并确保 /tmp 可写。

## 第二次：交互暂停，给自己留断点窗口

自动 init 会直接执行 all。若要使用 `LAB_STEP=1`，在**本学习目录**的 `labs/init` 中把 `/process_lab all` 那段替换为：

```sh
while :; do
  /bin/sh
  echo 'shell exited; PID 1 keeps running'
done
```

保留前面的 mount，重新运行 build-initramfs。此时 PID 1 管理循环，子 shell 提供交互入口；在 shell 执行：

```sh
LAB_STEP=1 /process_lab cow
LAB_STEP=1 /process_lab exec
LAB_STEP=1 /process_lab zombie
```

每个 CHECKPOINT 后按 Enter。cow 父子使用管道协作，阶段中只有预期一方等键盘，别用 Ctrl-D 当 Enter。调试结束可 `poweroff -f`。修改 init 后要重建 initramfs，QEMU 不会自动读取宿主刚改的脚本。

原始自动 init 的版本可从 `labs/init-auto.sh` 恢复。实验代码里的 sleep 只扩大 pipe 观察窗口，其他实验依靠 pipe/wait/join 确定顺序。

## 第三次：trace 比无条件断 schedule 更容易看全貌

在 guest 挂载 tracefs：

```sh
mkdir -p /sys/kernel/tracing
mount -t tracefs tracefs /sys/kernel/tracing
ls /sys/kernel/tracing/events/sched
```

附带 trace.sh 使用 bash，最小 BusyBox initramfs 没有 bash；要在配有 bash 的实验 rootfs 使用它，或用下面 BusyBox 可执行的短方案：

```sh
T=/sys/kernel/tracing/instances/process-study
mkdir "$T"
echo 0 > "$T/tracing_on"
echo 1 > "$T/events/sched/sched_process_fork/enable"
echo 1 > "$T/events/sched/sched_process_exec/enable"
echo 1 > "$T/events/sched/sched_process_exit/enable"
echo 1 > "$T/events/sched/sched_switch/enable"
echo 1 > "$T/events/sched/sched_waking/enable"
echo 1 > "$T/events/sched/sched_wakeup/enable"
echo 1 > "$T/tracing_on"
/process_lab pipe
echo 0 > "$T/tracing_on"
cat "$T/trace"
# 读完后移除本次专用 instance；目录名若已存在，先检查是否有人正在使用。
rmdir "$T"
```

实际手工执行时 mkdir 若失败就停止，不要继续写已有 instance。Bash 版以独立 PID 命名，并用 trap 清理，适合保存日志：`bash labs/trace.sh ./labs/process_lab pipe > trace.log 2> trace-stats.log`。

## 事件字段要看 format

`cat events/sched/sched_switch/format` 能确认 prev_pid、next_pid、prev_state。进程 fork 事件有 parent_pid/child_pid，exec 事件有对应身份字段；以目标内核导出的 format 为准。

`set_event_pid` 默认按事件记录时 current 过滤，不能笼统地理解成“只保留事件里提及该 PID 的记录”。唤醒由别的任务执行时尤其易漏。初学先短时间全量捕获，再按事件字段筛选；需要在线过滤时对 sched_switch 使用 `prev_pid == X || next_pid == X`，对 fork 使用 parent/child 字段，跨 fork 跟随选项另查内核支持。

ring buffer 可能覆盖记录；检查 per_cpu/cpu*/stats 的 overrun/dropped 信息。没有记录既可能没发生，也可能配置、过滤、覆盖或时钟关联出了问题。

## function_graph 是可选升级

当前已有内核未启用 CONFIG_FUNCTION_TRACER，所以不要直接 `echo function_graph > current_tracer`。先检查 `available_tracers`。确需函数图时，在独立 Linux 构建输出目录配置 FUNCTION_TRACER/FUNCTION_GRAPH_TRACER 等依赖，重建匹配的内核与符号后再做。

启用后也不是完整静态调用树：inline、notrace、汇编、不可跟踪函数以及优化会缺失。把动态 trace 当作本次执行的证据，与源码附录的静态主线对照，不能要求一字不差。
