# 12 一个 read 为什么会把 CPU 让出去

## 以空管道为具体场景

父子都有 pipe 的相应端。孩子 read 时，管道暂时没有字节，但还有写端存在：read 不能直接判定 EOF，需要等待数据。内核把任务接到等待队列、设置可睡眠状态、重查条件后调用 schedule。CPU 去运行父亲或其他任务。

父亲 write 后更新管道内容并唤醒相关等待者。唤醒路径使孩子重新可运行；等调度器选中，孩子从原来的等待位置继续，重新检查条件，再完成 read。孩子不会重新开始整个程序。

`fs/pipe.c:pipe_read/pipe_write` 是具体入口；`include/linux/wait.h` 的 wait_event 宏、`kernel/sched/wait.c` 与 `kernel/sched/core.c:try_to_wake_up` 是机制入口。

## 为什么必须“加入队列+设状态+重查条件”

错误模型：先检查没有数据，然后很久以后再准备睡。期间写端可能已经写入并发出唤醒；读端尚未可唤醒，就丢失通知，之后睡死。

正确等待协议通过锁、顺序和循环协调：发布等待者与睡眠状态，检查条件，若条件已满足就不用睡；不满足才调度；被唤醒后再检查。`wake_up` 不是把条件自动改成真，可能有多个竞争者或其他唤醒原因。

```text
等待者                              事件提供者
挂接 waitqueue / 设置睡眠状态        获取适当锁
检查条件                            修改共享条件/数据
  真：finish_wait 并继续              释放或按协议交接锁
  假：schedule                      wake_up
恢复后循环检查条件                   try_to_wake_up → 入队/发重调度通知
finish_wait
```

这不是可以自行去掉锁抄写的并发算法；具体锁和内存屏障由各等待 API 与共享状态协议确定。

## try_to_wake_up 不负责运行完目标函数

它校验目标状态、协调 pi_lock/on_rq/on_cpu 等并发状态，选择 CPU、激活任务，可能通过远端唤醒队列和 IPI 处理。唤醒后目标可以稍后才执行。如果它已经运行或不在匹配状态，不会机械重复入队。

新生任务初次唤醒用 `wake_up_new_task`；现有睡眠任务一般通过 wake_up_process/等待队列走 `try_to_wake_up`。这也是调试 fork 和调试 pipe 应选不同入口的原因。

## completion、mutex、futex 的位置

completion 是内核中“某件事完成”的同步机制，本章前面的 kthreadd_done、vfork_done 都是实例。mutex 是睡眠锁，竞争时可阻塞；spinlock 不能按一般睡眠锁那样持有后任意 schedule。

futex 是用户同步的内核等待/唤醒支撑，用户地址上的值判断与内核排队相结合；无竞争时 pthread mutex 等操作往往可主要在用户态完成。pthread_join 等待线程结束时可利用 clear_child_tid 清零和 futex 唤醒。不能看到 pthread API 就认为每次操作一定 syscall。

## 实验判据

`process_lab pipe` 中父亲写之前延迟一秒，是为了提高孩子进入阻塞状态的观察概率；正确性仍由 pipe 与 wait 保证。是否**真的阻塞过**应由 trace 或调度计数确认，单靠有一秒 sleep 不能保证所有调度条件下的每次运行都命中该状态。

打开 sched_switch、sched_waking、sched_wakeup，寻找子 PID 的切出、唤醒、切入。再到管道读函数里对照等待条件。分别记录：谁发起唤醒、孩子在哪个 CPU 入队、何时开始执行。

检查题：收到 wakeup 就说明读到了数据吗？不说明。唤醒与条件满足不是严格一对一，代码必须重新检查。
