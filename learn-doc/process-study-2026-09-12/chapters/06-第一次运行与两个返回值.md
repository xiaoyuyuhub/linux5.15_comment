# 06 子进程没有调用过 schedule，为什么能从里面“返回”

## 这是构造出来的初始现场

源码入口 `arch/x86/kernel/process.c:copy_thread`。它在新任务内核栈上定位 `pt_regs`，找到包含它的 `fork_frame`，获得 `inactive_task_frame`。

```text
新 task
  thread.sp ───────→ fork_frame
                    ┌ inactive_task_frame
                    │  保存的 callee-saved 寄存器槽
                    │  ret_addr = ret_from_fork
                    └ pt_regs
                       用户 RIP、RSP、RAX、段选择子、标志等
```

`thread.sp` 是未来切入时的内核栈指针，不是用户栈顶；`childregs->sp` 是未来用户态 RSP。两个 sp 搞反，后面的 GDB 会完全看不懂。

源码做：`frame->ret_addr=(unsigned long)ret_from_fork`，`p->thread.sp=(unsigned long)fork_frame`。于是调度器第一次切到这个任务时，会像恢复一个曾经停止的现场那样恢复寄存器，而预制的返回地址把 CPU 引导到 ret_from_fork。

## 普通 fork 子分支返回 0 的根因

```c
frame->bx = 0;
*childregs = *current_pt_regs();
childregs->ax = 0;
if (sp)
    childregs->sp = sp;
```

用户态父程序进入系统调用时，寄存器现场保存到父内核栈。复制后，子任务将来返回到相同的用户逻辑位置，但返回值槽 RAX 被改成 0。父任务则沿原有 `kernel_clone` 调用栈得到子 PID，再由系统调用出口放入自己的返回值。

因此不是“同一个 C 函数魔法般返回两遍”。是两个执行实体各自返回用户态，带着相似程序位置和不同 RAX。子任务也不是重新执行 main，从 fork 后面的判断继续。

用户 libc 还可能在系统调用返回后执行库内清理或 atfork 回调，所以“用户第一条指令”未必就是源文件 `if (pid==0)`。

## ret_from_fork 的两条路

`arch/x86/entry/entry_64.S:ret_from_fork` 先把刚切出的 prev 传给 `schedule_tail` 完成切换尾部处理。然后检查 RBX：

|RBX|来源|后续|
|---|---|---|
|0|普通用户子任务 copy_thread 设置|syscall_exit_to_user_mode → 寄存器恢复 → 用户态|
|内核函数地址|PF_KTHREAD 分支的 kthread_frame_init|R12 传参数，调用 RBX 指向的入口|

普通 kthread 的包装函数会调用线程函数并 `do_exit`；启动 PID 1 的 kernel_init 成功 exec 后可以返回 ret_from_fork，后者按注释所述继续返回用户態。这两个生命周期不要混为一谈。

`schedule_tail` 也处理 CLONE_CHILD_SETTID 的子 TID 写入以及信号相关状态。fork 创建时设置参数与孩子运行时执行动作是不同时间点。

## 一次能跟住的断点练习

1. 在 `copy_thread` 停下，确认参数 p 是子任务。
2. 走过 `childregs=task_pt_regs(p)` 后打印 childregs、p->thread.sp、frame->ret_addr。入口第一行就打印局部变量可能是未初始化值。
3. 走过普通用户分支后打印 childregs->ax、childregs->ip、childregs->sp。
4. 下 `ret_from_fork` 断点，并记录当前 PID；启动会频繁命中内核线程，先隔离目标实验 PID。
5. 在 ret_from_fork 看 `$rbx` 和 `$r12`，区分用户分支与内核入口。

优化导致变量缺失时：用 `disassemble /m copy_thread` 找到对应存储指令，在函数调用边界按 x86-64 ABI 查看寄存器。不能在任意指令位置都认为 `$rdi` 仍是第一个参数。

## 已运行任务与新任务的共同接口

已运行的 B 被切出时，B 的栈保存真实返回现场；后来恢复它会接着运行 B 的旧调用栈。新 B 没有历史，就由 copy_thread 人工做一个兼容现场。调度器不需要维护两套完全不同的底层切换机制。

检查题：为什么不把子进程内核栈整个 memcpy 成父栈，就让它继续？因为内核执行栈里有父任务专属局部状态和持锁状态；Linux 使用专门初始框架与返回入口建立正确的新执行上下文。
