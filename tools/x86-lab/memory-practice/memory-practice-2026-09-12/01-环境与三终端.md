# 01 环境、构建与三终端协作

## 1. 三层机器与三类文件

```text
Mac arm64
├─ 编辑源码、运行包装脚本、打开观察终端
└─ Lima Ubuntu arm64
   ├─ x86_64-linux-gnu-gcc 生成 x86_64 静态 ELF
   ├─ gdb-multiarch 读取 vmlinux 并连 QEMU stub
   └─ qemu-system-x86_64 (TCG)
      └─ Linux 5.15 x86_64 guest 执行实验程序
```

`vmlinux` 是 GDB 的内核符号文件，`bzImage` 是 QEMU 启动文件，`memory-practice.ext4` 是只装实验程序的独立数据盘。Mac 编译出的 Mach-O 和 Lima 默认编译器生成的 ARM64 ELF 都不能在 x86 guest 中运行。

## 2. 构建：只构建实验，不重构内核

Mac 终端执行：

```bash
cd /Users/xuyu/Desktop/code/linux5.15_comment
$HOME/.local/bin/limactl start linux-x86-builder
bash tools/x86-lab/memory-practice/build.sh
```

输出目录只有 `out/x86-lab/memory-practice/`。脚本用 `-O0 -g3 -fno-omit-frame-pointer -static -no-pie` 编译一个统一主程序和五个拆分对照程序，再生成 32 MiB ext4。它不调用完整内核构建，也不改 `rootfs.ext4`。

如果 `bzImage/vmlinux/rootfs.ext4` 本身不存在，才运行：

```bash
bash tools/x86-lab/build/build.sh
```

## 3. 启动模式

| 命令 | QEMU 状态 | 用途 |
|---|---|---|
| `run.sh` | 立即启动，无 GDB 端口 | 只运行程序 |
| `run.sh --gdb` | 立即启动，开放 1236 | 用户程序到 CHECKPOINT 后再附加 GDB |
| `run.sh --debug` | 第一条 CPU 指令前暂停，开放 1236 | 可选：回查启动期内存初始化 |

推荐第一次：

```bash
bash tools/x86-lab/memory-practice/run.sh --gdb
```

默认 1236 是本实践包的独立 GDB 端口，避免与现有 direct Lab 的 1234、旧 user-memory Lab 的 1235 冲突；需要时仍可用 `GDB_PORT=其他端口` 同时覆盖 `run.sh` 和 `gdb-kernel.sh`。

出现 `~ #` 后，在 guest 主控制台执行：

```sh
mkdir -p /mnt/mm
mount -o ro /dev/sdb /mnt/mm
ls -l /mnt/mm/bin
```

`/dev/sda` 是基础根盘，`/dev/sdb` 是实验盘；两者都由 QEMU snapshot 保护。实验盘没有分区表，所以不是 `/dev/sdb1`。

## 4. 三个终端各做一件事

### 终端 A：QEMU 主串口，推进实验

```sh
/mnt/mm/bin/00_memory_tour mmap
```

每次看到 `CHECKPOINT`，先不要按 Enter。记录 PID、BASE、下一动作；去终端 B 看状态，去终端 C 下针对本地址的断点；最后回来按 Enter。启动期内存初始化不是这条主线的前置条件：此时内核已启动完成，我们专门追用户进程的当次申请、缺页和释放。

### 终端 B：第二串口，只观察 guest

先在终端 A 启动第二串口 shell：

```sh
/mnt/mm/start-observer-console
```

再在新的 Mac 终端：

```bash
cd /Users/xuyu/Desktop/code/linux5.15_comment
bash tools/x86-lab/memory-practice/connect-observer.sh
```

连接后按一次 Enter，应看到第二个 guest shell。它和主终端处于同一台 guest、同一个 `/proc`，因此这里的 PID 才能观察主终端程序：

```sh
/mnt/mm/mm-observe 目标PID
cat /proc/目标PID/maps
cat /proc/目标PID/smaps_rollup
cat /proc/buddyinfo
cat /proc/zoneinfo
```

不要在 Mac 的 `/proc` 或 Lima 的 `/proc` 查这个 PID；三层系统的 PID 空间互不相同。

### 终端 C：GDB 控制整个 QEMU

```bash
cd /Users/xuyu/Desktop/code/linux5.15_comment
bash tools/x86-lab/memory-practice/gdb-kernel.sh
```

启动后会列出 `lab-help` 命令。GDB 一连接，整台 guest 会暂停；输入 `continue` 后两个串口恢复。这不是故障，也不是用户程序单进程调试器的行为。

## 5. 建议的观察记录表

每个 CHECKPOINT 记录一行：

| 阶段 | PID | 虚拟区间 | maps 是否存在 | mincore | VmRSS/RssAnon | GDB 命中 | 你认为改变的对象 |
|---|---:|---|---|---|---|---|---|
| A1 | | | | | | | VMA |
| A2 | | | | | | | zero-page/PTE |
| A3 | | | | | | | page/PTE |

全局 `MemFree`、`buddyinfo` 会受到 shell、GDB、打印和内核后台活动影响，不能期待每按一次 Enter 都精确减少一页。先用目标地址、目标 VMA、目标 PID 和 fault 调用栈证明因果，全局计数只作背景证据。

## 6. 结束与重建

退出 QEMU：`Ctrl-A`，松开，再按 `x`。修改 C 后先退出旧 QEMU，再运行 `build.sh` 和 `run.sh`；运行中的虚拟机不会自动看到新实验盘。因为是 snapshot，guest 中的临时修改在退出后丢失。
