# 02 启动期内存初始化：从固件内存图到 buddy 有库存

这一轮不用用户程序。目标是亲眼看到同一批 RAM 依次处于四种状态：被发现、被早期记录、拥有 `struct page/zone` 描述、最后进入 buddy 可分配链表。

## 1. 启动方式

终端 A：

```bash
cd /Users/xuyu/Desktop/code/linux5.15_comment
bash tools/x86-lab/memory-practice/run.sh --debug
```

终端 C：

```bash
bash tools/x86-lab/memory-practice/gdb-kernel.sh
```

GDB 连接后：

```gdb
lab-init
info breakpoints
continue
```

硬件断点槽有限。`lab-init` 一次列出路线方便学习，但不要让全部早期 `hbreak` 长期同时启用；若 GDB 报资源不足，`delete breakpoints` 后每次只下下一个断点。

## 2. 建议分三次启动，不要一次追完

### 第一次：入口和 x86 物理内存视图

```gdb
delete breakpoints
hbreak start_kernel
hbreak setup_arch
continue
```

在 `setup_arch` 中围绕以下源码阅读：

```text
arch/x86/kernel/setup.c: setup_arch
  → early_reserve_memory
  → e820__memory_setup
  → e820__memblock_setup
  → init_mem_mapping
  → initmem_init
  → paging_init
```

要回答：E820 是谁报告的物理地址布局？memblock 的 `memory` 与 `reserved` 为什么必须分开？direct mapping 是“内核能访问 RAM”的映射，为何不等于 buddy 已经能分配这些页？

可以在串口日志中寻找：

```text
BIOS-provided physical RAM map
Memory: ... available
```

### 第二次：给每个 PFN 建身份与 zone 容器

```gdb
delete breakpoints
hbreak paging_init
hbreak free_area_init
continue
```

当前 x86_64 主线：

```text
paging_init
  → sparse_init
  → zone_sizes_init
     → free_area_init
        → free_area_init_node
           → free_area_init_core
        → memmap_init
           → __init_single_page
```

在 `free_area_init` 入口：

```gdb
bt 6
p/x max_zone_pfn[0]
p/x max_zone_pfn[1]
p/x max_zone_pfn[2]
```

数组下标要结合本构建的 zone 枚举解释，不要脱离配置死记。此阶段 `pgdat`、zone、`free_area[order]` 和 `struct page` 框架在建立，但这不等于所有未保留页已在 free list 中。

### 第三次：真正把页交给 buddy

重新启动，或删除旧断点并继续到：

```gdb
delete breakpoints
hbreak build_all_zonelists
hbreak mem_init
hbreak memblock_free_all
continue
```

关键顺序：

```text
start_kernel
  → build_all_zonelists        建未来的 zone/node 搜索路线
  → page_alloc_init            注册 PCP CPU 生命周期回调
  → mm_init                    通用 MM 收尾
     → mem_init                x86 收尾
        → memblock_free_all    未保留 RAM 批量入 buddy
           → __free_pages_core
              → __free_pages_ok
                 → __free_one_page
```

`build_all_zonelists` 只建搜索顺序，不生产库存；`page_alloc_init` 也不是把全部 RAM 放入 PCP。真正的 early allocator → buddy 交接锚点是 `memblock_free_all`。

## 3. 观察数据结构时问什么

| 对象 | 你该问的问题 | 不应得出的结论 |
|---|---|---|
| E820 entry | 哪些物理地址被固件称为 RAM/reserved？ | 全部 RAM 都能被随便用 |
| memblock.memory | 内核早期知道哪些 RAM？ | 已经在 buddy free list |
| memblock.reserved | 内核镜像、页表等占了哪些区间？ | reserved 永远不释放 |
| `struct page` | PFN 的内核账本在哪里、属于哪个 node/zone？ | 它是实际 4 KiB 数据本身 |
| `zone->free_area[order]` | 每种阶的空闲块链表和数量如何？ | 每个链表节点都对应 order-0 |
| zonelist | 分配失败时按什么 zone/node 顺序回退？ | 它拥有或复制了页 |

## 4. 为什么启动期断点只用一次

标记为 `__init` 的代码在启动后会被 `free_initmem` 回收。系统进入 shell 后再给这些地址下断点，没有办法让这次已完成的启动重新经过它们；必须重启 QEMU。断点命中后及时记录并删除，避免在代码回收后保留误导性的断点。

## 5. 本轮验收

你应能不看文档说出：

```text
E820 发现 RAM
→ memblock 管早期 memory/reserved
→ direct map 让内核能访问物理 RAM
→ sparse/vmemmap 建 PFN 到 struct page
→ free_area_init 建 node/zone/buddy 空容器
→ zonelist 建分配搜索路线
→ memblock_free_all 把未保留页真正放入 buddy
→ SLUB/vmalloc/正式 PCP 等上层设施继续初始化
```

并能解释“已经被描述”与“已经可分配”为什么是两个阶段。
