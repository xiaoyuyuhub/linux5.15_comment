# 04 用户态申请方式逐项对比

这一章不把“申请内存”当成单一 API。每种方式都问四件事：谁选择虚拟地址？何时建立/改变 VMA？何时获得物理页？释放由谁决定是否归还内核？下面命令均先用统一主程序；标题中的 `02`～`05` 是对应的独立小程序，需要缩小调试范围时再用。

## 1. `02_populate`：lazy 与 `MAP_POPULATE`

```sh
/mnt/mm/bin/00_memory_tour populate
```

它建立两段相同长度的匿名映射：普通映射和带 `MAP_POPULATE` 的映射。P1 时比较两行 `mincore`。

```text
普通 mmap：       系统调用主要建立 VMA，数据页通常等访问再 fault
MAP_POPULATE：    mmap 返回前主动预填充页表/触发 fault-in
```

因此调试 `MAP_POPULATE` 时，匿名页分配可能发生在 `mmap` 系统调用尚未返回的上下文中，不要等待用户态写入后才下 fault 断点。它仍不是物理连续分配承诺，也不是长期锁页；页面以后仍可能被回收。要长期要求驻留是 `mlock` 的另一套权限与限制语义。

GDB 可在 P0：

```gdb
break do_mmap
break __mm_populate
continue
```

`mm_populate` 是内联包装，本内核构建中可稳定下断的符号是 `__mm_populate`。如果以后更换内核配置后符号变化，先 `info functions populate`，再从 `do_mmap` 单步或按当前源码调用点下行断点。

## 2. `03_malloc_brk`：对象分配器与内核边界

```sh
/mnt/mm/bin/00_memory_tour malloc
```

程序把 glibc 的 mmap threshold 请求设置为 128 KiB，然后申请 64 B 和 1 MiB，打印每步 program break。这个设置是让两条路径更容易观察，不是 Linux 内核规则，也不保证所有 libc 实现完全按同一策略运行。

| 现象 | 合理解释 | 不能直接证明 |
|---|---|---|
| 64 B 返回且 BRK 不变 | allocator 复用已有 arena/chunk | malloc 不会触页 |
| 64 B 后 BRK 增长 | allocator 向 brk heap 要了更多范围 | 只为这 64 B 精确增长 |
| 1 MiB 地址是独立 maps 区间 | 大对象很可能由 mmap 支撑 | 所有大于 128 KiB 永远 mmap |
| free 后 maps 消失 | 对应大映射可能 munmap | 所有 free 都进内核 |
| free 后 BRK 不回退 | heap 空间被 allocator 保留复用 | 内存泄漏 |

小块常见边界：

```text
malloc
→ 用户态 arena/tcache/chunk 查找
→ 不足时可能 brk(new_end)
→ do_brk_flags 建立或扩大 heap VMA
→ malloc 返回对象地址
→ allocator 元数据或用户访问可能触页
```

大块常见边界：

```text
malloc
→ 用户态策略选择 mmap
→ 匿名 VMA
→ 首次触页
→ free 可能 munmap 整块
```

GDB 不含匹配 glibc 源码时，先在内核边界证明，而不是假装逐行理解 libc：

```gdb
break __x64_sys_brk
break __x64_sys_mmap
break __x64_sys_munmap
continue
```

在每个 CHECKPOINT 用 `/proc/PID/maps` 对照 `[heap]` 边界和大对象地址。系统调用可能来自程序启动、stdio 或其他库活动；必须判断参数/返回地址是否覆盖打印出的 SMALL/LARGE。

## 3. `04_fork_cow`：已经有物理页，写时仍会 fault

```sh
/mnt/mm/bin/00_memory_tour cow
```

父进程先写匿名页为 `P`，再 fork。C1 时会打印父 PID、子 PID、同一个 BASE；子进程正在管道上等待。此刻父子虚拟地址数值相同，PTE 通常指向同一物理页并被写保护，以便写时复制。

在 C1 抄下 BASE 和 CHILD_PID，GDB：

```gdb
delete breakpoints
lab-cow 0x实际BASE
continue
```

回主终端按 Enter，子进程执行写入。典型主线：

```text
用户写一个 present 但只读的 PTE
→ x86 write-protection page fault
→ handle_mm_fault
→ do_wp_page
→ wp_page_copy
→ 分配新页并复制旧内容
→ 子 PTE 指向新页且可写
→ 父 PTE 仍指向旧页
```

实验输出要求 `CHILD_AFTER_WRITE ... VALUE=C`，随后父进程必须仍输出 `VALUE=P`。这证明的是地址空间隔离/COW 结果。要证明具体物理页变化，还需在断点处记录 `orig_pte`、新页和两边页表，不能只凭字符结果声称 PFN 细节。

`do_wp_page` 也可处理其他写保护原因。地址条件能缩小范围，但不同进程可能拥有相同虚拟地址；用 CHILD_PID、调用时机以及 `vmf->vma->vm_mm` 共同确认。本构建的 Linux GDB 辅助命令可用时，可以追加 `$lx_current().pid == CHILD_PID`；不可用时不要硬写 `current` 宏条件。

## 4. `05_file_map`：page cache、共享写回与私有 COW

```sh
/mnt/mm/bin/00_memory_tour file
```

程序在 `/tmp` 创建两页文件，对同一 fd 建 `MAP_SHARED` 和 `MAP_PRIVATE` 两段映射。

```text
首次读文件映射
→ file-backed fault
→ 地址空间/page cache 查找或读入 folio/page
→ 建立用户 PTE

写 MAP_SHARED
→ 修改 page cache 中共享的文件页
→ msync 要求把脏数据同步到底层文件

写 MAP_PRIVATE
→ 私有写保护 fault
→ COW 匿名页
→ 私有视图变成 P；底层文件和 shared 视图仍为 S
```

F2 后预期文件内容是 `S`；F3 后预期 `file=S shared=S private=P`。`MAP_PRIVATE` 不是“把整个文件映射时立即复制一遍”，复制通常发生在实际写到相应页时。

可以从通用入口逐步分流：

```gdb
break handle_mm_fault
break filemap_fault
break do_wp_page
continue
```

不要三者长期无条件开启。先在 CHECKPOINT 停住，按 SHARED/PRIVATE 地址设置 `address` 或 `vmf->address` 条件，再执行下一次访问。

## 5. 常见用户态方式总表

| 方式 | 虚拟区间来源 | 首次物理页时机 | 释放/回收入口 | 本包 |
|---|---|---|---|---|
| 小块 `malloc/calloc/realloc` | allocator 复用或 brk/mmap | allocator 或用户首次访问 | `free` 先到 allocator | `03` |
| 大块 malloc | 常见为匿名 mmap | 首次触页或预填充 | free 可能 munmap | `03` |
| `brk/sbrk` | 扩缩传统 heap VMA | 首次访问 | 缩 brk/进程退出 | `03` 观察边界 |
| 匿名 `mmap` | 独立匿名 VMA | 首次 fault | munmap/退出 | `01` |
| `MAP_POPULATE` | mmap VMA | mmap 返回前预填充 | munmap/回收 | `02` |
| 文件 `MAP_SHARED` | file-backed VMA | fault 进入 page cache | munmap；脏页另行写回 | `05` |
| 文件 `MAP_PRIVATE` | file-backed VMA | 读可共享 cache，写时 COW | munmap/退出 | `05` |
| fork COW | 继承父 VMA/PTE | 写保护 fault 时复制 | 各 mm 独立解除 | `04` |
| 栈自动增长 | grow-down 栈 VMA |访问新栈页 fault | 线程/进程退出 | 后续练习 |
| SysV/POSIX shared memory | 共享内存对象映射 | fault/预填充 | detach/unmap + 对象生命周期 | 后续练习 |
| hugetlb/THP | 巨页 VMA/策略 | 巨页 fault/折叠 | 巨页专用路径 | 当前 THP 关闭，不在本轮 |

`kmalloc/kzalloc/kmem_cache_alloc/vmalloc/alloc_pages` 是内核态 API，不是用户程序能直接调用的替代 malloc。它们值得单独做模块或内核内建实验，但那会改变内核配置/代码，故与本独立用户态实践包分开。
