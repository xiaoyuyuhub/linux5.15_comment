{\footnotesize\ttfamily void synchronize\+\_\+srcu (\begin{DoxyParamCaption}\item[{struct \mbox{\hyperlink{structsrcu__struct}{srcu\+\_\+struct}} $\ast$}]{ssp }\end{DoxyParamCaption})}

synchronize\+\_\+srcu -\/ wait for prior S\+R\+CU read-\/side critical-\/section completion @ssp\+: \mbox{\hyperlink{structsrcu__struct}{srcu\+\_\+struct}} with which to synchronize.

Wait for the count to drain to zero of both indexes. To avoid the possible starvation of \mbox{\hyperlink{srcutree_8c_a7067934d25cef40739986f9673b56df0}{synchronize\+\_\+srcu()}}, it waits for the count of the index=((-\/$>$srcu\+\_\+idx \& 1) $^\wedge$ 1) to drain to zero at first, and then flip the srcu\+\_\+idx and wait for the count of the other index.

Can block; must be called from process context.

Note that it is illegal to call \mbox{\hyperlink{srcutree_8c_a7067934d25cef40739986f9673b56df0}{synchronize\+\_\+srcu()}} from the corresponding S\+R\+CU read-\/side critical section; doing so will result in deadlock. However, it is perfectly legal to call \mbox{\hyperlink{srcutree_8c_a7067934d25cef40739986f9673b56df0}{synchronize\+\_\+srcu()}} on one \mbox{\hyperlink{structsrcu__struct}{srcu\+\_\+struct}} from some other \mbox{\hyperlink{structsrcu__struct}{srcu\+\_\+struct}}\textquotesingle{}s read-\/side critical section, as long as the resulting graph of srcu\+\_\+structs is acyclic.

There are memory-\/ordering constraints implied by \mbox{\hyperlink{srcutree_8c_a7067934d25cef40739986f9673b56df0}{synchronize\+\_\+srcu()}}. On systems with more than one C\+PU, when \mbox{\hyperlink{srcutree_8c_a7067934d25cef40739986f9673b56df0}{synchronize\+\_\+srcu()}} returns, each C\+PU is guaranteed to have executed a full memory barrier since the end of its last corresponding S\+R\+CU read-\/side critical section whose beginning preceded the call to \mbox{\hyperlink{srcutree_8c_a7067934d25cef40739986f9673b56df0}{synchronize\+\_\+srcu()}}. In addition, each C\+PU having an S\+R\+CU read-\/side critical section that extends beyond the return from \mbox{\hyperlink{srcutree_8c_a7067934d25cef40739986f9673b56df0}{synchronize\+\_\+srcu()}} is guaranteed to have executed a full memory barrier after the beginning of \mbox{\hyperlink{srcutree_8c_a7067934d25cef40739986f9673b56df0}{synchronize\+\_\+srcu()}} and before the beginning of that S\+R\+CU read-\/side critical section. Note that these guarantees include C\+P\+Us that are offline, idle, or executing in user mode, as well as C\+P\+Us that are executing in the kernel.

Furthermore, if C\+PU A invoked \mbox{\hyperlink{srcutree_8c_a7067934d25cef40739986f9673b56df0}{synchronize\+\_\+srcu()}}, which returned to its caller on C\+PU B, then both C\+PU A and C\+PU B are guaranteed to have executed a full memory barrier during the execution of \mbox{\hyperlink{srcutree_8c_a7067934d25cef40739986f9673b56df0}{synchronize\+\_\+srcu()}}. This guarantee applies even if C\+PU A and C\+PU B are the same C\+PU, but again only if the system has more than one C\+PU.

Of course, these memory-\/ordering guarantees apply only when \mbox{\hyperlink{srcutree_8c_a7067934d25cef40739986f9673b56df0}{synchronize\+\_\+srcu()}}, \mbox{\hyperlink{srcu_8h_a264085619f023909acb39ad5e025e0ea}{srcu\+\_\+read\+\_\+lock()}}, and \mbox{\hyperlink{srcu_8h_a00f3580fd0e28f982971a242b3ed5cb4}{srcu\+\_\+read\+\_\+unlock()}} are passed the same \mbox{\hyperlink{structsrcu__struct}{srcu\+\_\+struct}} structure.

Implementation of these memory-\/ordering guarantees is similar to that of \mbox{\hyperlink{tiny_8c_a2a82b0ecedfdd3957789e90bdfd47756}{synchronize\+\_\+rcu()}}.

If S\+R\+CU is likely idle, expedite the first request. This semantic was provided by Classic S\+R\+CU, and is relied upon by its users, so T\+R\+EE S\+R\+CU must also provide it. Note that detecting idleness is heuristic and subject to both false positives and negatives.
