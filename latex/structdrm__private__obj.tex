\doxysubsection{Detailed Description}
struct \mbox{\hyperlink{structdrm__private__obj}{drm\+\_\+private\+\_\+obj}} -\/ base struct for driver private atomic object

A driver private object is initialized by calling \mbox{\hyperlink{drm__atomic_8h_a86392be00db189418cb88aec9092dac3}{drm\+\_\+atomic\+\_\+private\+\_\+obj\+\_\+init()}} and cleaned up by calling \mbox{\hyperlink{drm__atomic_8h_a767dd9dfed3b11a3caeee19e6f9e6346}{drm\+\_\+atomic\+\_\+private\+\_\+obj\+\_\+fini()}}.

Currently only tracks the state update functions and the opaque driver private state itself, but in the future might also track which \&\mbox{\hyperlink{structdrm__modeset__lock}{drm\+\_\+modeset\+\_\+lock}} is required to duplicate and update this object\textquotesingle{}s state.

All private objects must be initialized before the D\+RM device they are attached to is registered to the D\+RM subsystem (call to \mbox{\hyperlink{drm__drv_8h_aa400aa845e16d611d6db9ee0e7e6726e}{drm\+\_\+dev\+\_\+register()}}) and should stay around until this D\+RM device is unregistered (call to \mbox{\hyperlink{drm__drv_8h_a76d71d9781c22fe668ccc867b96e91e9}{drm\+\_\+dev\+\_\+unregister()}}). In other words, private objects lifetime is tied to the D\+RM device lifetime. This implies that\+:

1/ all calls to \mbox{\hyperlink{drm__atomic_8h_a86392be00db189418cb88aec9092dac3}{drm\+\_\+atomic\+\_\+private\+\_\+obj\+\_\+init()}} must be done before calling \mbox{\hyperlink{drm__drv_8h_aa400aa845e16d611d6db9ee0e7e6726e}{drm\+\_\+dev\+\_\+register()}} 2/ all calls to \mbox{\hyperlink{drm__atomic_8h_a767dd9dfed3b11a3caeee19e6f9e6346}{drm\+\_\+atomic\+\_\+private\+\_\+obj\+\_\+fini()}} must be done after calling \mbox{\hyperlink{drm__drv_8h_a76d71d9781c22fe668ccc867b96e91e9}{drm\+\_\+dev\+\_\+unregister()}}

If that private object is used to store a state shared by multiple C\+R\+T\+Cs, proper care must be taken to ensure that non-\/blocking commits are properly ordered to avoid a use-\/after-\/free issue.

Indeed, assuming a sequence of two non-\/blocking \&drm\+\_\+atomic\+\_\+commit on two different \&\mbox{\hyperlink{structdrm__crtc}{drm\+\_\+crtc}} using different \&\mbox{\hyperlink{structdrm__plane}{drm\+\_\+plane}} and \&\mbox{\hyperlink{structdrm__connector}{drm\+\_\+connector}}, so with no resources shared, there\textquotesingle{}s no guarantee on which commit is going to happen first. However, the second \&drm\+\_\+atomic\+\_\+commit will consider the first \&\mbox{\hyperlink{structdrm__private__obj}{drm\+\_\+private\+\_\+obj}} its old state, and will be in charge of freeing it whenever the second \&drm\+\_\+atomic\+\_\+commit is done.

If the first \&drm\+\_\+atomic\+\_\+commit happens after it, it will consider its \&\mbox{\hyperlink{structdrm__private__obj}{drm\+\_\+private\+\_\+obj}} the new state and will be likely to access it, resulting in an access to a freed memory region. Drivers should store (and get a reference to) the \&\mbox{\hyperlink{structdrm__crtc__commit}{drm\+\_\+crtc\+\_\+commit}} structure in our private state in \&\mbox{\hyperlink{structdrm__mode__config__helper__funcs_a147801d799a1580b1eb9332ceee2181f}{drm\+\_\+mode\+\_\+config\+\_\+helper\+\_\+funcs.\+atomic\+\_\+commit\+\_\+setup}}, and then wait for that commit to complete as the first step of \&\mbox{\hyperlink{structdrm__mode__config__helper__funcs_a6f1f9ffe4491edf41454da35bf2468de}{drm\+\_\+mode\+\_\+config\+\_\+helper\+\_\+funcs.\+atomic\+\_\+commit\+\_\+tail}}, similar to \mbox{\hyperlink{drm__atomic__helper_8h_a2dd1b08e06dcbbbd1e21efb9e0ac3324}{drm\+\_\+atomic\+\_\+helper\+\_\+wait\+\_\+for\+\_\+dependencies()}}.
