\mbox{\hyperlink{classThe}{The}} latch technique is a multiversion concurrency control method that allows queries during non-\/atomic modifications. If you can guarantee queries never interrupt the modification -- e.\+g. the concurrency is strictly between C\+P\+Us -- you most likely do not need this.

Where the traditional R\+C\+U/lockless data structures rely on atomic modifications to ensure queries observe either the old or the new state the latch allows the same for non-\/atomic updates. \mbox{\hyperlink{classThe}{The}} trade-\/off is doubling the cost of storage; we have to maintain two copies of the entire data structure.

Very simply put\+: we first modify one copy and then the other. This ensures there is always one copy in a stable state, ready to give us an answer.

\mbox{\hyperlink{classThe}{The}} basic form is a data structure like\+:\+:

struct latch\+\_\+struct \{ \mbox{\hyperlink{structseqcount__latch__t}{seqcount\+\_\+latch\+\_\+t}} seq; struct data\+\_\+struct data\mbox{[}2\mbox{]}; \};

Where a modification, which is assumed to be externally serialized, does the following\+:\+:

void latch\+\_\+modify(struct latch\+\_\+struct $\ast$latch, ...) \{ \mbox{\hyperlink{include_2asm-generic_2barrier_8h_af5af5daeacc75c413fb9a3f910e9fb32}{smp\+\_\+wmb()}}; // Ensure that the last data\mbox{[}1\mbox{]} update is visible latch-\/$>$seq.\+sequence++; \mbox{\hyperlink{include_2asm-generic_2barrier_8h_af5af5daeacc75c413fb9a3f910e9fb32}{smp\+\_\+wmb()}}; // Ensure that the seqcount update is visible

modify(latch-\/$>$data\mbox{[}0\mbox{]}, ...);

\mbox{\hyperlink{include_2asm-generic_2barrier_8h_af5af5daeacc75c413fb9a3f910e9fb32}{smp\+\_\+wmb()}}; // Ensure that the data\mbox{[}0\mbox{]} update is visible latch-\/$>$seq.\+sequence++; \mbox{\hyperlink{include_2asm-generic_2barrier_8h_af5af5daeacc75c413fb9a3f910e9fb32}{smp\+\_\+wmb()}}; // Ensure that the seqcount update is visible

modify(latch-\/$>$data\mbox{[}1\mbox{]}, ...); \}

\mbox{\hyperlink{classThe}{The}} query will have a form like\+:\+:

struct entry $\ast$latch\+\_\+query(struct latch\+\_\+struct $\ast$latch, ...) \{ struct entry $\ast$entry; unsigned seq, idx;

do \{ seq = raw\+\_\+read\+\_\+seqcount\+\_\+latch(\&latch-\/$>$seq);

idx = seq \& 0x01; entry = data\+\_\+query(latch-\/$>$data\mbox{[}idx\mbox{]}, ...);

// This includes needed \mbox{\hyperlink{include_2asm-generic_2barrier_8h_a9b849177daf3d9558280d4af104d7f46}{smp\+\_\+rmb()}} \} while (read\+\_\+seqcount\+\_\+latch\+\_\+retry(\&latch-\/$>$seq, seq));

return entry; \}

So during the modification, queries are first redirected to data\mbox{[}1\mbox{]}. Then we modify data\mbox{[}0\mbox{]}. When that is complete, we redirect queries back to data\mbox{[}0\mbox{]} and we can modify data\mbox{[}1\mbox{]}.

N\+O\+TE\+:

\mbox{\hyperlink{classThe}{The}} non-\/requirement for atomic modifications does {\itshape N\+OT} include the publishing of new entries in the case where data is a dynamic data structure.

An iteration might start in data\mbox{[}0\mbox{]} and get suspended long enough to miss an entire modification sequence, once it resumes it might observe the new entry.
