\doxysubsection{Detailed Description}
struct \mbox{\hyperlink{structrpmsg__endpoint}{rpmsg\+\_\+endpoint}} -\/ binds a local rpmsg address to its user @rpdev\+: rpmsg channel device @refcount\+: when this drops to zero, the ept is deallocated @cb\+: rx callback handler @cb\+\_\+lock\+: must be taken before accessing/changing @cb @addr\+: local rpmsg address @priv\+: private data for the driver\textquotesingle{}s use

In essence, an rpmsg endpoint represents a listener on the rpmsg bus, as it binds an rpmsg address with an rx callback handler.

Simple rpmsg drivers shouldn\textquotesingle{}t use this struct directly, because things just work\+: every rpmsg driver provides an rx callback upon registering to the bus, and that callback is then bound to its rpmsg address when the driver is probed. When relevant inbound messages arrive (i.\+e. messages which their dst address equals to the src address of the rpmsg channel), the driver\textquotesingle{}s handler is invoked to process it.

More complicated drivers though, that do need to allocate additional rpmsg addresses, and bind them to different rx callbacks, must explicitly create additional endpoints by themselves (see \mbox{\hyperlink{linux_2rpmsg_8h_a9da390cd74474d2dde1bffeb0d0d2bfe}{rpmsg\+\_\+create\+\_\+ept()}}).
