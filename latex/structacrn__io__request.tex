\doxysubsection{Detailed Description}
struct \mbox{\hyperlink{structacrn__io__request}{acrn\+\_\+io\+\_\+request}} -\/ 256-\/byte A\+C\+RN I/O request @type\+: \mbox{\hyperlink{protocolType-p}{Type}} of this request (A\+C\+R\+N\+\_\+\+I\+O\+R\+E\+Q\+\_\+\+T\+Y\+P\+E\+\_\+$\ast$). @completion\+\_\+polling\+: Polling flag. Hypervisor will poll completion of the I/O request if this flag set. @reserved0\+: Reserved fields. @reqs\+: Union of different types of request. Byte offset\+: 64. @reqs.pio\+\_\+request\+: P\+IO request data of the I/O request. @reqs.pci\+\_\+request\+: P\+CI configuration space request data of the I/O request. @reqs.mmio\+\_\+request\+: M\+M\+IO request data of the I/O request. @reqs.data\+: Raw data of the I/O request. @reserved1\+: Reserved fields. @kernel\+\_\+handled\+: Flag indicates this request need be handled in kernel. @processed\+: \mbox{\hyperlink{classThe}{The}} status of this request (A\+C\+R\+N\+\_\+\+I\+O\+R\+E\+Q\+\_\+\+S\+T\+A\+T\+E\+\_\+$\ast$).

\mbox{\hyperlink{classThe}{The}} state transitions of A\+C\+RN I/O request\+:

F\+R\+EE -\/$>$ P\+E\+N\+D\+I\+NG -\/$>$ P\+R\+O\+C\+E\+S\+S\+I\+NG -\/$>$ C\+O\+M\+P\+L\+E\+TE -\/$>$ F\+R\+EE -\/$>$ ...

An I/O request in C\+O\+M\+P\+L\+E\+TE or F\+R\+EE state is owned by the hypervisor. H\+SM and A\+C\+RN userspace are in charge of processing the others.

On basis of the states illustrated above, a typical lifecycle of A\+C\+RN IO request would look like\+:

Flow (assume the initial state is F\+R\+EE) $\vert$ $\vert$ Service VM v\+C\+PU 0 Service VM v\+C\+PU x User v\+C\+PU y $\vert$ $\vert$ hypervisor\+: $\vert$ fills in type, addr, etc. $\vert$ pauses the User VM v\+C\+PU y $\vert$ sets the state to P\+E\+N\+D\+I\+NG (a) $\vert$ fires an upcall to Service VM $\vert$ $\vert$ H\+SM\+: $\vert$ scans for P\+E\+N\+D\+I\+NG requests $\vert$ sets the states to P\+R\+O\+C\+E\+S\+S\+I\+NG (b) $\vert$ assigns the requests to clients (c) V $\vert$ client\+: $\vert$ scans for the assigned requests $\vert$ handles the requests (d) $\vert$ H\+SM\+: $\vert$ sets states to C\+O\+M\+P\+L\+E\+TE $\vert$ notifies the hypervisor $\vert$ $\vert$ hypervisor\+: $\vert$ resumes User VM v\+C\+PU y (e) $\vert$ $\vert$ hypervisor\+: $\vert$ post handling (f) V sets states to F\+R\+EE

Note that the procedures (a) to (f) in the illustration above require to be strictly processed in the order. One v\+C\+PU cannot trigger another request of I/O emulation before completing the previous one.

Atomic and barriers are required when H\+SM and hypervisor accessing the state of \&struct \mbox{\hyperlink{structacrn__io__request}{acrn\+\_\+io\+\_\+request}}.
