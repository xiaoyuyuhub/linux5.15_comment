\+\_\+\+\_\+anon\+\_\+vma\+\_\+prepare -\/ attach an \mbox{\hyperlink{structanon__vma}{anon\+\_\+vma}} to a memory region @vma\+: the memory region in question

This makes sure the memory mapping described by \textquotesingle{}vma\textquotesingle{} has an \textquotesingle{}\mbox{\hyperlink{structanon__vma}{anon\+\_\+vma}}\textquotesingle{} attached to it, so that we can associate the anonymous pages mapped into it with that \mbox{\hyperlink{structanon__vma}{anon\+\_\+vma}}.

\mbox{\hyperlink{classThe}{The}} common case will be that we already have one, which is handled inline by \mbox{\hyperlink{rmap_8h_a1f0f6b8bab2cd4051a0703173d04333d}{anon\+\_\+vma\+\_\+prepare()}}. But if not we either need to find an adjacent mapping that we can re-\/use the \mbox{\hyperlink{structanon__vma}{anon\+\_\+vma}} from (very common when the only reason for splitting a vma has been mprotect()), or we allocate a new one.

Anon-\/vma allocations are very subtle, because we may have optimistically looked up an \mbox{\hyperlink{structanon__vma}{anon\+\_\+vma}} in \mbox{\hyperlink{rmap_8c_afd75b12714f3964faf9b971163fd3b76}{page\+\_\+lock\+\_\+anon\+\_\+vma\+\_\+read()}} and that may actually touch the rwsem even in the newly allocated vma (it depends on R\+CU to make sure that the \mbox{\hyperlink{structanon__vma}{anon\+\_\+vma}} isn\textquotesingle{}t actually destroyed).

As a result, we need to do proper \mbox{\hyperlink{structanon__vma}{anon\+\_\+vma}} locking even for the new allocation. At the same time, we do not want to do any locking for the common case of already having an \mbox{\hyperlink{structanon__vma}{anon\+\_\+vma}}.
