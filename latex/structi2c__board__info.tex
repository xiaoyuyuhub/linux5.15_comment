\doxysubsection{Detailed Description}
struct \mbox{\hyperlink{structi2c__board__info}{i2c\+\_\+board\+\_\+info}} -\/ template for device creation @type\+: chip type, to initialize \mbox{\hyperlink{structi2c__client_aeb39329cef5d7ac69183ec17f51b3442}{i2c\+\_\+client.\+name}} @flags\+: to initialize \mbox{\hyperlink{structi2c__client_a4e0c34e4e2d228496ca7f7e627b95ab7}{i2c\+\_\+client.\+flags}} @addr\+: stored in \mbox{\hyperlink{structi2c__client_a1798622200b46ac5dc220659b40eb8af}{i2c\+\_\+client.\+addr}} @dev\+\_\+name\+: Overrides the default $<$busnr$>$-\/$<$addr$>$ dev\+\_\+name if set @platform\+\_\+data\+: stored in i2c\+\_\+client.\+dev.\+platform\+\_\+data @of\+\_\+node\+: pointer to Open\+Firmware device node @fwnode\+: device node supplied by the platform firmware @swnode\+: software node for the device @resources\+: resources associated with the device @num\+\_\+resources\+: number of resources in the @resources array @irq\+: stored in \mbox{\hyperlink{structi2c__client_af6da8a644c5bdd18b01da69aac1b487e}{i2c\+\_\+client.\+irq}}

I2C doesn\textquotesingle{}t actually support hardware probing, although controllers and devices may be able to use I2\+C\+\_\+\+S\+M\+B\+U\+S\+\_\+\+Q\+U\+I\+CK to tell whether or not there\textquotesingle{}s a device at a given address. Drivers commonly need more information than that, such as chip type, configuration, associated I\+RQ, and so on.

\mbox{\hyperlink{structi2c__board__info}{i2c\+\_\+board\+\_\+info}} is used to build tables of information listing I2C devices that are present. This information is used to grow the driver model tree. For mainboards this is done statically using \mbox{\hyperlink{linux_2i2c_8h_a21324b7bf52b8a744113c35a565b3046}{i2c\+\_\+register\+\_\+board\+\_\+info()}}; bus numbers identify adapters that aren\textquotesingle{}t yet available. For add-\/on boards, i2c\+\_\+new\+\_\+client\+\_\+device() does this dynamically with the adapter already known.
