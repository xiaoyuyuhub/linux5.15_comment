\doxysubsubsection{\texorpdfstring{kfree\_rcu}{kfree\_rcu}}
{\footnotesize\ttfamily \#define kfree\+\_\+rcu(\begin{DoxyParamCaption}\item[{}]{\mbox{\hyperlink{uapi_2sound_2asequencer_8h_add9af9569af79ec26dd741fb226b38ba}{ptr}},  }\item[{}]{rhf... }\end{DoxyParamCaption})~\mbox{\hyperlink{rcupdate_8h_a534a4aaeda18644b54b0a9227393cfab}{kvfree\+\_\+rcu}}(\mbox{\hyperlink{uapi_2sound_2asequencer_8h_add9af9569af79ec26dd741fb226b38ba}{ptr}}, \#\# rhf)}

\mbox{\hyperlink{rcupdate_8h_ab386d1226fbabf13ca203599dfa54c94}{kfree\+\_\+rcu()}} -\/ kfree an object after a grace period. @ptr\+: pointer to kfree for both single-\/ and double-\/argument invocations. @rhf\+: the name of the struct rcu\+\_\+head within the type of @ptr, but only for double-\/argument invocations.

Many rcu callbacks functions just call \mbox{\hyperlink{include_2linux_2slab_8h_ad92c2890c435f9cca9e36ff4f97feb5c}{kfree()}} on the base structure. These functions are trivial, but their size adds up, and furthermore when they are used in a kernel module, that module must invoke the high-\/latency \mbox{\hyperlink{tiny_8c_a7ac3474e3971b47e01b1a5f5c590d8ee}{rcu\+\_\+barrier()}} function at module-\/unload time.

\mbox{\hyperlink{classThe}{The}} \mbox{\hyperlink{rcupdate_8h_ab386d1226fbabf13ca203599dfa54c94}{kfree\+\_\+rcu()}} function handles this issue. Rather than encoding a function address in the embedded rcu\+\_\+head structure, \mbox{\hyperlink{rcupdate_8h_ab386d1226fbabf13ca203599dfa54c94}{kfree\+\_\+rcu()}} instead encodes the offset of the rcu\+\_\+head structure within the base structure. Because the functions are not allowed in the low-\/order 4096 bytes of kernel virtual memory, offsets up to 4095 bytes can be accommodated. If the offset is larger than 4095 bytes, a compile-\/time error will be generated in \mbox{\hyperlink{rcupdate_8h_a43889685ac766cfaa65000cd1377de5d}{kvfree\+\_\+rcu\+\_\+arg\+\_\+2()}}. \mbox{\hyperlink{rcupdate_8h_a08376f3ea7b11ce473fcac3babf45d7e}{rcu\+\_\+assign\+\_\+pointer()}} -\/ assign to R\+C\+U-\/protected pointer {\ttfamily }\+: pointer to assign to @v\+: value to assign (publish)

Assigns the specified value to the specified R\+C\+U-\/protected pointer, ensuring that any concurrent R\+CU readers will see any prior initialization.

Inserts memory barriers on architectures that require them (which is most of them), and also prevents the compiler from reordering the code that initializes the structure after the pointer assignment. More importantly, this call documents which pointers will be dereferenced by R\+CU read-\/side code.

In some special cases, you may use \mbox{\hyperlink{rcupdate_8h_ad30f6689018c0dc0178126e1e12897e9}{R\+C\+U\+\_\+\+I\+N\+I\+T\+\_\+\+P\+O\+I\+N\+T\+E\+R()}} instead of \mbox{\hyperlink{rcupdate_8h_a08376f3ea7b11ce473fcac3babf45d7e}{rcu\+\_\+assign\+\_\+pointer()}}. \mbox{\hyperlink{rcupdate_8h_ad30f6689018c0dc0178126e1e12897e9}{R\+C\+U\+\_\+\+I\+N\+I\+T\+\_\+\+P\+O\+I\+N\+T\+E\+R()}} is a bit faster due to the fact that it does not constrain either the C\+PU or the compiler. That said, using \mbox{\hyperlink{rcupdate_8h_ad30f6689018c0dc0178126e1e12897e9}{R\+C\+U\+\_\+\+I\+N\+I\+T\+\_\+\+P\+O\+I\+N\+T\+E\+R()}} when you should have used \mbox{\hyperlink{rcupdate_8h_a08376f3ea7b11ce473fcac3babf45d7e}{rcu\+\_\+assign\+\_\+pointer()}} is a very bad thing that results in impossible-\/to-\/diagnose memory corruption. So please be careful. See the \mbox{\hyperlink{rcupdate_8h_ad30f6689018c0dc0178126e1e12897e9}{R\+C\+U\+\_\+\+I\+N\+I\+T\+\_\+\+P\+O\+I\+N\+T\+E\+R()}} comment header for details.

Note that \mbox{\hyperlink{rcupdate_8h_a08376f3ea7b11ce473fcac3babf45d7e}{rcu\+\_\+assign\+\_\+pointer()}} evaluates each of its arguments only once, appearances notwithstanding. One of the \char`\"{}extra\char`\"{} evaluations is in \mbox{\hyperlink{trace__event__perf_8c_a75ebc7dc6a947606a5be3a1e1b02fb61}{typeof()}} and the other visible only to sparse ({\bfseries{C\+H\+E\+C\+K\+ER}}), neither of which actually execute the argument. R\+C\+U\+\_\+\+N\+O\+N\+I\+D\+LE -\/ Indicate idle-\/loop code that needs R\+CU readers {\itshape }\+: Code that R\+CU needs to pay attention to.

R\+CU read-\/side critical sections are forbidden in the inner idle loop, that is, between the \mbox{\hyperlink{tree_8c_aabd0d60f3fe5c1ca0e601af88936201b}{rcu\+\_\+idle\+\_\+enter()}} and the \mbox{\hyperlink{tree_8c_a603009c10e15ff89ce191ffd4844e38d}{rcu\+\_\+idle\+\_\+exit()}} -- R\+CU will happily ignore any such read-\/side critical sections. This macro provides the way out\+: \mbox{\hyperlink{rcupdate_8h_ae35545f43afe03e2839125d67bc3c76b}{R\+C\+U\+\_\+\+N\+O\+N\+I\+D\+L\+E(do\+\_\+something\+\_\+with\+\_\+\+R\+C\+U())}} will tell R\+CU that it needs to pay attention, invoke its argument (in this example, calling the do\+\_\+something\+\_\+with\+\_\+\+R\+C\+U() function), and then tell R\+CU to go back to ignoring this C\+PU. It is permissible to nest \mbox{\hyperlink{rcupdate_8h_ae35545f43afe03e2839125d67bc3c76b}{R\+C\+U\+\_\+\+N\+O\+N\+I\+D\+L\+E()}} wrappers, but not indefinitely (but the limit is on the order of a million or so, even on 32-\/bit systems). \mbox{\hyperlink{tree_8c_a094a548179ef967658b67414a0c91d32}{call\+\_\+rcu()}} -\/ Queue an R\+CU callback for invocation after a grace period. @head\+: structure to be used for queueing the R\+CU updates. @func\+: actual callback function to be invoked after the grace period

\mbox{\hyperlink{classThe}{The}} callback function will be invoked some time after a full grace period elapses, in other words after all pre-\/existing R\+CU read-\/side critical sections have completed. However, the callback function might well execute concurrently with R\+CU read-\/side critical sections that started after \mbox{\hyperlink{tree_8c_a094a548179ef967658b67414a0c91d32}{call\+\_\+rcu()}} was invoked.

R\+CU read-\/side critical sections are delimited by \mbox{\hyperlink{rcupdate_8h_a039341af5d714114b6c2eb8e6ed305e6}{rcu\+\_\+read\+\_\+lock()}} and \mbox{\hyperlink{rcupdate_8h_a07db93454b6994cf0af302584e84ffb9}{rcu\+\_\+read\+\_\+unlock()}}, and may be nested. This includes hardware interrupt handlers, softirq handlers, and N\+MI handlers.

Note that all C\+P\+Us must agree that the grace period extended beyond all pre-\/existing R\+CU read-\/side critical section. On systems with more than one C\+PU, this means that when \char`\"{}func()\char`\"{} is invoked, each C\+PU is guaranteed to have executed a full memory barrier since the end of its last R\+CU read-\/side critical section whose beginning preceded the call to \mbox{\hyperlink{tree_8c_a094a548179ef967658b67414a0c91d32}{call\+\_\+rcu()}}. \mbox{\hyperlink{rcupdate_8h_a039341af5d714114b6c2eb8e6ed305e6}{rcu\+\_\+read\+\_\+lock()}} -\/ mark the beginning of an R\+CU read-\/side critical section

When \mbox{\hyperlink{rcupdate_8h_a2a82b0ecedfdd3957789e90bdfd47756}{synchronize\+\_\+rcu()}} is invoked on one C\+PU while other C\+P\+Us are within R\+CU read-\/side critical sections, then the \mbox{\hyperlink{rcupdate_8h_a2a82b0ecedfdd3957789e90bdfd47756}{synchronize\+\_\+rcu()}} is guaranteed to block until after all the other C\+P\+Us exit their critical sections. Similarly, if \mbox{\hyperlink{rcupdate_8h_a094a548179ef967658b67414a0c91d32}{call\+\_\+rcu()}} is invoked on one C\+PU while other C\+P\+Us are within R\+CU read-\/side critical sections, invocation of the corresponding R\+CU callback is deferred until after the all the other C\+P\+Us exit their critical sections.

In v5.\+0 and later kernels, \mbox{\hyperlink{rcupdate_8h_a2a82b0ecedfdd3957789e90bdfd47756}{synchronize\+\_\+rcu()}} and \mbox{\hyperlink{rcupdate_8h_a094a548179ef967658b67414a0c91d32}{call\+\_\+rcu()}} also wait for regions of code with preemption disabled, including regions of code with interrupts or softirqs disabled. In pre-\/v5.\+0 kernels, which define synchronize\+\_\+sched(), only code enclosed within \mbox{\hyperlink{rcupdate_8h_a039341af5d714114b6c2eb8e6ed305e6}{rcu\+\_\+read\+\_\+lock()}} and \mbox{\hyperlink{rcupdate_8h_a07db93454b6994cf0af302584e84ffb9}{rcu\+\_\+read\+\_\+unlock()}} are guaranteed to be waited for.

Note, however, that R\+CU callbacks are permitted to run concurrently with new R\+CU read-\/side critical sections. One way that this can happen is via the following sequence of events\+: (1) C\+PU 0 enters an R\+CU read-\/side critical section, (2) C\+PU 1 invokes \mbox{\hyperlink{rcupdate_8h_a094a548179ef967658b67414a0c91d32}{call\+\_\+rcu()}} to register an R\+CU callback, (3) C\+PU 0 exits the R\+CU read-\/side critical section, (4) C\+PU 2 enters a R\+CU read-\/side critical section, (5) the R\+CU callback is invoked. This is legal, because the R\+CU read-\/side critical section that was running concurrently with the \mbox{\hyperlink{rcupdate_8h_a094a548179ef967658b67414a0c91d32}{call\+\_\+rcu()}} (and which therefore might be referencing something that the corresponding R\+CU callback would free up) has completed before the corresponding R\+CU callback is invoked.

R\+CU read-\/side critical sections may be nested. Any deferred actions will be deferred until the outermost R\+CU read-\/side critical section completes.

But if you want the full story, read on!

{\footnotesize\ttfamily void synchronize\+\_\+rcu (\begin{DoxyParamCaption}\item[{void}]{ }\end{DoxyParamCaption})}

synchronize\+\_\+rcu -\/ wait until a grace period has elapsed.

Control will return to the caller some time after a full grace period has elapsed, in other words after all currently executing R\+CU read-\/side critical sections have completed. Note, however, that upon return from \mbox{\hyperlink{tree_8c_a2a82b0ecedfdd3957789e90bdfd47756}{synchronize\+\_\+rcu()}}, the caller might well be executing concurrently with new R\+CU read-\/side critical sections that began while \mbox{\hyperlink{tree_8c_a2a82b0ecedfdd3957789e90bdfd47756}{synchronize\+\_\+rcu()}} was waiting.

R\+CU read-\/side critical sections are delimited by \mbox{\hyperlink{rcupdate_8h_a039341af5d714114b6c2eb8e6ed305e6}{rcu\+\_\+read\+\_\+lock()}} and \mbox{\hyperlink{rcupdate_8h_a07db93454b6994cf0af302584e84ffb9}{rcu\+\_\+read\+\_\+unlock()}}, and may be nested. In addition, but only in v5.\+0 and later, regions of code across which interrupts, preemption, or softirqs have been disabled also serve as R\+CU read-\/side critical sections. This includes hardware interrupt handlers, softirq handlers, and N\+MI handlers.

Note that this guarantee implies further memory-\/ordering guarantees. On systems with more than one C\+PU, when \mbox{\hyperlink{tree_8c_a2a82b0ecedfdd3957789e90bdfd47756}{synchronize\+\_\+rcu()}} returns, each C\+PU is guaranteed to have executed a full memory barrier since the end of its last R\+CU read-\/side critical section whose beginning preceded the call to \mbox{\hyperlink{tree_8c_a2a82b0ecedfdd3957789e90bdfd47756}{synchronize\+\_\+rcu()}}. In addition, each C\+PU having an R\+CU read-\/side critical section that extends beyond the return from \mbox{\hyperlink{tree_8c_a2a82b0ecedfdd3957789e90bdfd47756}{synchronize\+\_\+rcu()}} is guaranteed to have executed a full memory barrier after the beginning of \mbox{\hyperlink{tree_8c_a2a82b0ecedfdd3957789e90bdfd47756}{synchronize\+\_\+rcu()}} and before the beginning of that R\+CU read-\/side critical section. Note that these guarantees include C\+P\+Us that are offline, idle, or executing in user mode, as well as C\+P\+Us that are executing in the kernel.
