\mbox{\hyperlink{bitmap_8h_af9a7701c440a5e7e3775b8d2804c77a9}{B\+I\+T\+M\+A\+P\+\_\+\+F\+R\+O\+M\+\_\+\+U64()}} -\/ Represent u64 value in the format suitable for bitmap. ~\newline
\+: u64 value

Linux bitmaps are internally arrays of unsigned longs, i.\+e. 32-\/bit integers in 32-\/bit environment, and 64-\/bit integers in 64-\/bit one.

There are four combinations of endianness and length of the word in linux A\+B\+Is\+: L\+E64, B\+E64, L\+E32 and B\+E32.

On 64-\/bit kernels 64-\/bit LE and BE numbers are naturally ordered in bitmaps and therefore don\textquotesingle{}t require any special handling.

On 32-\/bit kernels 32-\/bit LE A\+BI orders lo word of 64-\/bit number in memory prior to hi, and 32-\/bit BE orders hi word prior to lo. \mbox{\hyperlink{classThe}{The}} bitmap on the other hand is represented as an array of 32-\/bit words and the position of bit N may therefore be calculated as\+: word \#(N/32) and bit \#(N\%32) in that word. For example, bit \#42 is located at 10th position of 2nd word. It matches 32-\/bit LE A\+BI, and we can simply let the compiler store 64-\/bit values in memory as it usually does. But for BE we need to swap hi and lo words manually.

With all that, the macro \mbox{\hyperlink{bitmap_8h_af9a7701c440a5e7e3775b8d2804c77a9}{B\+I\+T\+M\+A\+P\+\_\+\+F\+R\+O\+M\+\_\+\+U64()}} does explicit reordering of hi and lo parts of u64. For L\+E32 it does nothing, and for BE environment it swaps hi and lo words, as is expected by bitmap. \mbox{\Hypertarget{bitmap_8h_a5c43feb200294801cfa8352824c0a40b}\label{bitmap_8h_a5c43feb200294801cfa8352824c0a40b}}

D\+OC\+: bitmap introduction

bitmaps provide an array of bits, implemented using an array of unsigned longs. \mbox{\hyperlink{classThe}{The}} number of valid bits in a given bitmap does {\itshape not} need to be an exact multiple of B\+I\+T\+S\+\_\+\+P\+E\+R\+\_\+\+L\+O\+NG.

\mbox{\hyperlink{classThe}{The}} possible unused bits in the last, partially used word of a bitmap are \textquotesingle{}don\textquotesingle{}t care\textquotesingle{}. \mbox{\hyperlink{classThe}{The}} implementation makes no particular effort to keep them zero. It ensures that their value will not affect the results of any operation. \mbox{\hyperlink{classThe}{The}} bitmap operations that return Boolean (bitmap\+\_\+empty, for example) or scalar (bitmap\+\_\+weight, for example) results carefully filter out these unused bits from impacting their results.

\mbox{\hyperlink{classThe}{The}} \mbox{\hyperlink{bitmap_8c_ac0d69e120401272c34828a2f981c025e}{bitmap\+\_\+print\+\_\+to\+\_\+pagebuf()}} is used indirectly via its cpumap wrapper \mbox{\hyperlink{include_2linux_2cpumask_8h_ab5bfc83160ddd6b30e5815ad763888ca}{cpumap\+\_\+print\+\_\+to\+\_\+pagebuf()}} or directly by drivers to export hexadecimal bitmask and decimal list to userspace by sysfs A\+BI. Drivers might be using a normal attribute for this kind of A\+B\+Is. A normal attribute typically has show entry as below\+: static ssize\+\_\+t example\+\_\+attribute\+\_\+show(struct device $\ast$dev, struct \mbox{\hyperlink{structdevice__attribute}{device\+\_\+attribute}} $\ast$attr, char $\ast$buf) \{ ... return bitmap\+\_\+print\+\_\+to\+\_\+pagebuf(true, buf, \&mask, nr\+\_\+trig\+\_\+max); \} show entry of attribute has no offset and count parameters and this means the file is limited to one page only. \mbox{\hyperlink{bitmap_8c_ac0d69e120401272c34828a2f981c025e}{bitmap\+\_\+print\+\_\+to\+\_\+pagebuf()}} A\+PI works terribly well for this kind of normal attribute with buf parameter and without offset, count\+: bitmap\+\_\+print\+\_\+to\+\_\+pagebuf(bool list, char $\ast$buf, const unsigned long $\ast$maskp, int nmaskbits) \{ \} \mbox{\hyperlink{classThe}{The}} problem is once we have a large bitmap, we have a chance to get a bitmask or list more than one page. Especially for list, it could be as complex as 0,3,5,7,9,... We have no simple way to know it exact size. It turns out \mbox{\hyperlink{structbin__attribute}{bin\+\_\+attribute}} is a way to break this limit. \mbox{\hyperlink{structbin__attribute}{bin\+\_\+attribute}} has show entry as below\+: static ssize\+\_\+t example\+\_\+bin\+\_\+attribute\+\_\+show(struct file $\ast$filp, struct kobject $\ast$kobj, struct \mbox{\hyperlink{structbin__attribute}{bin\+\_\+attribute}} $\ast$attr, char $\ast$buf, loff\+\_\+t offset, size\+\_\+t count) \{ ... \} With the new offset and count parameters, this makes sysfs A\+BI be able to support file size more than one page. For example, offset could be $>$= 4096. \mbox{\hyperlink{bitmap_8c_aa610650c928802a1d9ded36265cd8e19}{bitmap\+\_\+print\+\_\+bitmask\+\_\+to\+\_\+buf()}}, \mbox{\hyperlink{bitmap_8c_ae2a690ffe76165444948077a14e63418}{bitmap\+\_\+print\+\_\+list\+\_\+to\+\_\+buf()}} wit their cpumap wrapper \mbox{\hyperlink{include_2linux_2cpumask_8h_a8d1ac4d8be93888133204817fecfa0fc}{cpumap\+\_\+print\+\_\+bitmask\+\_\+to\+\_\+buf()}}, \mbox{\hyperlink{include_2linux_2cpumask_8h_a071fb3fd8bd887f82d72f6326391ddca}{cpumap\+\_\+print\+\_\+list\+\_\+to\+\_\+buf()}} make those drivers be able to support large bitmask and list after they move to use \mbox{\hyperlink{structbin__attribute}{bin\+\_\+attribute}}. \mbox{\hyperlink{classThe}{The}} role of \mbox{\hyperlink{include_2linux_2cpumask_8h_a8d1ac4d8be93888133204817fecfa0fc}{cpumap\+\_\+print\+\_\+bitmask\+\_\+to\+\_\+buf()}} and \mbox{\hyperlink{include_2linux_2cpumask_8h_a071fb3fd8bd887f82d72f6326391ddca}{cpumap\+\_\+print\+\_\+list\+\_\+to\+\_\+buf()}} is similar with \mbox{\hyperlink{include_2linux_2cpumask_8h_ab5bfc83160ddd6b30e5815ad763888ca}{cpumap\+\_\+print\+\_\+to\+\_\+pagebuf()}}, the difference is that \mbox{\hyperlink{bitmap_8c_ac0d69e120401272c34828a2f981c025e}{bitmap\+\_\+print\+\_\+to\+\_\+pagebuf()}} mainly serves sysfs attribute with the assumption the destination buffer is exactly one page and won\textquotesingle{}t be more than one page. \mbox{\hyperlink{include_2linux_2cpumask_8h_a8d1ac4d8be93888133204817fecfa0fc}{cpumap\+\_\+print\+\_\+bitmask\+\_\+to\+\_\+buf()}} and \mbox{\hyperlink{include_2linux_2cpumask_8h_a071fb3fd8bd887f82d72f6326391ddca}{cpumap\+\_\+print\+\_\+list\+\_\+to\+\_\+buf()}}, on the other hand, mainly serves \mbox{\hyperlink{structbin__attribute}{bin\+\_\+attribute}} which doesn\textquotesingle{}t work with exact one page, and it can break the size limit of converted decimal list and hexadecimal bitmask.

W\+A\+R\+N\+I\+N\+G!

This function is not a replacement for \mbox{\hyperlink{boot_2boot_8h_ac38cd16373d98782e1465bd3d5aba470}{sprintf()}} or \mbox{\hyperlink{bitmap_8c_ac0d69e120401272c34828a2f981c025e}{bitmap\+\_\+print\+\_\+to\+\_\+pagebuf()}}. It is intended to workaround sysfs limitations discussed above and should be used carefully in general case for the following reasons\+:
\begin{DoxyItemize}
\item Time complexity is O(nbits$^\wedge$2/count), comparing to O(nbits) for \mbox{\hyperlink{vsprintf_8c_aed3a44ce00b8d92f93e8a34e7b9dbf54}{snprintf()}}.
\item Memory complexity is O(nbits), comparing to O(1) for \mbox{\hyperlink{vsprintf_8c_aed3a44ce00b8d92f93e8a34e7b9dbf54}{snprintf()}}.
\item @off and @count are N\+OT offset and number of bits to print.
\item If printing part of bitmap as list, the resulting string is not a correct list representation of bitmap. Particularly, some bits within or out of related interval may be erroneously set or unset. \mbox{\hyperlink{classThe}{The}} format of the string may be broken, so bitmap\+\_\+parselist-\/like parser may fail parsing it.
\item If printing the whole bitmap as list by parts, user must ensure the order of calls of the function such that the offset is incremented linearly.
\item If printing the whole bitmap as list by parts, user must keep bitmap unchanged between the very first and very last call. Otherwise concatenated result may be incorrect, and format may be broken.
\end{DoxyItemize}
