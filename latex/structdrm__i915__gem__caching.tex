\doxysubsection{Detailed Description}
struct \mbox{\hyperlink{structdrm__i915__gem__caching}{drm\+\_\+i915\+\_\+gem\+\_\+caching}} -\/ Set or get the caching for given object handle.

Allow userspace to control the G\+TT caching bits for a given object when the object is later mapped through the pp\+G\+TT(or G\+G\+TT on older platforms lacking pp\+G\+TT support, or if the object is used for scanout). Note that this might require unbinding the object from the G\+TT first, if its current caching value doesn\textquotesingle{}t match.

Note that this all changes on discrete platforms, starting from D\+G1, the set/get caching is no longer supported, and is now rejected. Instead the C\+PU caching attributes(\+W\+B vs W\+C) will become an immutable creation time property for the object, along with the G\+TT caching level. For now we don\textquotesingle{}t expose any new u\+A\+PI for this, instead on D\+G1 this is all implicit, although this largely shouldn\textquotesingle{}t matter since D\+G1 is coherent by default(without any way of controlling it).

Implicit caching rules, starting from D\+G1\+: \begin{DoxyVerb}- If any of the object placements (see &drm_i915_gem_create_ext_memory_regions)
  contain I915_MEMORY_CLASS_DEVICE then the object will be allocated and
  mapped as write-combined only.

- Everything else is always allocated and mapped as write-back, with the
  guarantee that everything is also coherent with the GPU.
\end{DoxyVerb}


Note that this is likely to change in the future again, where we might need more flexibility on future devices, so making this all explicit as part of a new \&\mbox{\hyperlink{structdrm__i915__gem__create__ext}{drm\+\_\+i915\+\_\+gem\+\_\+create\+\_\+ext}} extension is probable.

Side note\+: Part of the reason for this is that changing the at-\/allocation-\/time C\+PU caching attributes for the pages might be required(and is expensive) if we need to then C\+PU map the pages later with different caching attributes. This inconsistent caching behaviour, while supported on x86, is not universally supported on other architectures. So for simplicity we opt for setting everything at creation time, whilst also making it immutable, on discrete platforms.
